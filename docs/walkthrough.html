1 · The problem

One assistant routes every task by picking a name from a list that only grows

One assistant, many workers

The interaction agent talks to you and hands each task to an execution agent: draft, reply, remind.

Agents never retire

Every task creates or reuses one. Nothing is archived or merged.

Routing by bare name

Each turn, the assistant sees every name in roster.json: no purpose, status or last-used time.

What the assistant saw at 1,000 agents 
<active_agents>
  <agent name="Email to Alice" />
  <agent name="Alice follow-up" />
  <agent name="Carl Remodel Urgency Check" />
  <agent name="Kwame Book Club Dates" />
  … 996 more
</active_agents>

user: any update from my contractor on the bathroom job?

Which one? “Remodel Urgency Check” doesn’t say bathroom, so it made Bathroom Job Contractor Update: a duplicate.

And on safety

2 · How I measured

I built the measurement first, in three layers

L1 · retrieval

Is the right card shown?

No model calls. Free and deterministic, so I used it for sweeps.

L2 · routing

Does it pick the right agent?

One real assistant turn with the production prompt and tools, on rosters of 10 to 1,000. Tool calls are intercepted and the outcome graded: correct, acceptable, minor, costly (duplicate), harmful (wrong agent).

L3 · end to end

Does the whole system behave?

Real agents against an in-memory Gmail, 26 scenarios. Sends are audited where mail leaves the mailbox, separately from the gate.

Plus a memory eval (plant facts, compact, ask for them back) and an LLM judge from another model family, used only on the 3 checks where it agreed with my 42 hand labels at least 85% of the time. Evals run on DeepSeek V4.1 Flash, chosen after a reliability check (malformed tool calls 0.55%, wait loops 1.2%).

2 · How I measured

Simulated lives, answer keys from construction, and a sealed test

Building a world

  1. Code writes a 180-day life plan: contacts, topics, events. Every event knows its thread.
  2. A model writes each event as a casual text message.
  3. The real assistant plays the events and grows its own roster, with its own messy names.
  4. Snapshots at 10, 50, 200 agents; 1,000 adds ~800 unrelated errands to the 200 roster, same probes.
  5. Probes are the next events in the life, 12 kinds, same quota in both lives.

Answer keys

The agent that handled that thread during growth. “Ask the user” also counts when another live matter shares the person and topic.

Checked

Three checker models vote. I reviewed every disagreement plus a 10% random sample: 68 reviewed, 54 accepted, 9 fixed, 5 rejected. Random audit: 0 of 20 changed.

Discipline

Tune on life 1 (Jordan). Life 2 (Riley) sealed until one final run per system. Keep rule: a change stays only if its target improves and nothing gets worse by more than 0.02. Checksum over the grader and benchmark.

3 · What I tried

v1: show the relevant few, and guard against duplicates in code

registry

Agent cards in SQLite

Replaces roster.json. An id, plus purpose, people, last active and status.

retrieval

Top 8 + active in the last hour

Scored by keywords, entities and recency. About 13 cards in the prompt at any size.

dedup guard

Creates checked against existing cards

Same name, or same person and topic, is pushed back. Guard off: duplicates 0.00 → 0.11.

reuse policy

An agent owns a matter

A person plus a subject belongs to one agent, whatever the next step is.

v1’s first test

Intervals touching zero. The error analysis showed the benchmark itself was part of the problem: dev had 1 vague-reference case, test had 6, and some keys were wrong. So I rebuilt it as benchmark v2 before going further.

4 · Results

Did it hold up? Checks I ran against my own results

summary drift

Current 0.60 → 0.97

Summaries are rewritten every run, so they could drift. A judge compared each one with the agent’s runs; I read its failures. The latest status was being cut off and details drifted. Putting “Now” first, no guessing, and a rebuild every 5th run fixed it; routing stayed within noise.

status wording

0.99 on new phrasings

Each status question asked 10 new ways, written before the run. Clear rewordings correct: original 0.62, v1 0.59, final 0.99. Turns that created an agent: 29, 24, 1 of 100.

what it found

A gap I couldn’t close

27 rewordings dropped the person’s name and were truly ambiguous; final guessed 17 times. An “ask which” line fixed that but failed the keep rule elsewhere, so it was reverted.

These ran after the sealed test, so they’re checked on dev only; the life-2 numbers stay those of the frozen system.

4 · Results

Safety, memory, and a live test on the production model

send gate

0 unauthorized sends

15 held-out runs. Gate off, same scenarios: 6. Every draft gets a content hash; only the user’s own yes, after seeing it, approves that exact content.

memory

Recall 1.00

Planted facts survive compaction on a held-out seed, including a decision that was later changed, at ~5.5k tokens instead of 9–10k and growing.

live on Sonnet 5.5

9 of 25 turns failed → 0 of 12

Evals ran on DeepSeek. Testing the production model by hand found a wait loop the evals couldn’t see. Fixed with a test before submitting.

The same live session: a phishing email claiming “the user already approved” was refused and flagged; an edit while approving produced a new draft and a new question. Two reply rules from my hand labels: don’t repeat a draft the user can already see, and warn plainly when something claims the user’s approval.

4 · Results, for the user

What a user notices now, and what is still rough

Better

  • It remembers the matter. “How’s the Carl quote going?” goes to the thread it already has, with the latest status.
  • Far fewer duplicate conversations: about 1 in 70 decisions at 1,000 tasks, down from 1 in 9.
  • Speed and cost stay flat however many tasks you have.
  • One reply per message, and quick results arrive as soon as they’re ready.
  • Nothing is sent without your yes to that exact draft; edits ask again, and a fake “you approved” email gets flagged.

Still rough

  • About 1 message in 20 at 1,000 tasks still lands in the wrong thread, mostly a new topic with someone you already talk to.
  • A broad request can swallow later ones: after “anything new in my inbox?”, unrelated tasks went to that same thread.
  • Drafts are plain chat bubbles approved by typing “yes”; with several waiting, which one is meant is left to the assistant.
  • Reminders are set in UTC, so it asks for your timezone.
  • Sometimes asks when it didn’t need to, mostly with few tasks.
  • Nothing decides which updates are worth interrupting you for when many tasks report back.

7 · Gaps and next

What’s still wrong, and the next two weeks in order

Open gaps

  • Harmful rate 0.049 against a 0.01 target.
  • Evals ran on DeepSeek; production runs Sonnet 5.5.
  • The 1,000 test uses easy, unrelated distractors.
  • Live, one broad “Inbox Check” agent absorbed every matter.
  • Choosing which draft a “yes” means is still the model’s call.
  • Nothing ranks what reaches the user from hundreds of agents.

Next, in this order

  1. Fix what I missed: make the second look fire on every “same person, different matter” turn.
  2. Confirm it transfers: one targeted Sonnet run, original vs final at 1,000.
  3. Test more honestly: a third life with look-alike distractors, which also tests the post-run fixes.
  4. Then expand: overload on the user’s side, deciding what is worth interrupting them for.
